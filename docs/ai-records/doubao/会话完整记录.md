## 一、这题到底是什么

## 二、核心机制拆解（含容易写错的边界）

### 1. 疑似重复检测

- 条件：同 `user` + 同 `merchant` + 同 `amount` + `|t_a − t_b| ≤ 10min` + 不同 `tx_id`。
- **每个无序对只建一条**：去重键 = `DUPLICATE + sorted(tx_a, tx_b)` 的 hash，靠唯一约束兜底。
- **必须"两两判断"，不能链式传递**：09:00/05/11 三笔，(00,05)✓、(05,11)=6min✓、(00,11)=11min✗ → 只有 2 条；题面 09:00/05/09（首尾 9min）→ C(3,2)=3 条，三条共享一个 cluster id 做"明确关联"。
- 措辞只能是"**疑似**"，禁止称"已证实错误扣款"。

### 2. 退款对账（乱序是重点）

- 一个 refund：申请确认时间（计时起点）、应退金额、若干到账记录。
- 到账事件**可能先于申请到达**（场景 5）：先存，等信息齐全再判，不得丢弃或报错。
- 判断顺序很重要：**先看是否已全额，再看是否逾期**。
  - 已到合计 = 应退 → 全额到账，可验证结案，**不发逾期**（哪怕申请时间因数据延迟看起来已过 72h）；
  - now ≥ 申请+72h 且 已到 < 应退 → 逾期提醒；
  - 部分到账 → 显示差额（应退−已到），如先到 60 则"剩 40"。

### 3. 提醒时间线（次数规则最绕）

```
 首次提醒          第1次追加          第2次追加
   │  nudge=0        │  nudge=1          │  nudge=2
   ├─── 24h ─────────┼──────── 24h ──────┤  之后不再催
   ▼                 ▼                   ▼
 issue建立        未回复且≥24h        未回复且≥24h
```

- 首次不计追加；未回复才追加，**最多 2 次**；
- 部分到账等**新数据不重置次数**、不重启 24h 周期；
- 用户标"**确有问题**"后 → 停止无回复催办（进入"已知问题待解决"，等事实或下一项约定）；
- "明天再提醒"：`next = max(已有的最早提醒时间, now+24h)`，**取较晚值、不清零**；只给日期没给时间 → 需澄清。

### 4. Issue 状态机（正常/解决/关闭必须分开）

```
            重复类                          退款类
  OPEN(疑似) ──首次提醒──► REMINDING    WAITING_DATA(信息未齐)
   │  ├ 标"两次正常"  → NORMAL(误报结案)   │
   │  ├ 标"确有问题"  → CONFIRMED_PROBLEM  ├ 72h未全额 → OVERDUE
   │  │                    └ 用户确认解决 → SELF_RESOLVED(结案)
   │  ├ 明天再提醒    → SNOOZED ─►回REMINDING
   │  └ 关闭          → CLOSED(冻结)        ├ 部分到账 → PARTIAL(显示差额)
   │                                        └ 全额到账 → RESOLVED_FULL(可验证结案)
   └────────────────  CLOSED：新事实只补记录，不自动重开；新独立交易对 → 新 Issue
```

结案依据要分清：**重复类靠用户明确确认（标"用户确认"，不称已验证退款）；退款类靠全额到账可验证；关闭是用户主动结案，与解决/正常并列**。发过提醒 ≠ 解决。

### 5. 持续工作与用户控制

- **自动驱动**：新数据到达或到点 → 自己跑评估，不等用户；
- **中断恢复**：已确认结果不丢、同一事实不重复处理（事件流幂等）；
- **暂停**：停主动提醒/新动作，可查；恢复时按最新数据评估，**不补发暂停期间错过的每一条**（只看"现在该发哪条"）；暂停/恢复不清次数和记录；
- **关闭**：停自动推进，重开需明确；已发消息保留；发送前已关闭则不发，发送后关闭不撤回；已提交但结果未知 → 标"未知"并核实，**不盲重试、不把关闭当撤销**；
- 多用户隔离；缺失/失败不得伪装成 0/成功/完成。

## 一、一个场景怎么检验：固定三段式（Given-When-Then）

每个场景都是一条独立用例，结构完全一样：

```
 Given  准备独立用户 + 喂入初始数据（交易/退款/到账）
 When   按剧本推进虚拟时间(+72h/+24h…)，每步调 tick；中途插入用户动作/重放
 Then   断言"可观察结果"：问题数量、状态、金额、差额、提醒次数与时间点、结案依据
```

三个硬性要求：
1. **虚拟时钟**：不真等，用 FixedClock 快进；
2. **场景隔离**：每个用例独立 user / 独立内存库（或每用例重建表），杜绝状态互相污染；
3. **重放断言**：题面反复要求"重放不新增/不累计"，所以每个场景末尾都要把同样的事件再喂一遍，断言结果不变。

## 二、10 个场景的检验规格（喂什么 / 推进到哪 / 断言什么）

| # | 输入与时间推进 | 关键断言（不是"返回200"） |
|---|---|---|
| 1 | 同商户 09:00、09:05 各 30 元，编号不同 | 问题数=**1**，类型=**疑似重复**，关联 2 笔交易，交易未被删除；重放仍 1 条 |
| 2 | 场景1 后，用户标记"两次正常"，再重放 | 状态=**正常（误报结案）**，历史有记录；重放不重开、不新增 |
| 3 | 09:00/05/09 三笔各 30 元 | 问题数=**3**（三个不同无序对），共享同一组关联；重放仍 3 条 |
| 4 | 应退 100 申请→+72h 未到→到 60→到 40 | +72h 发**逾期**（差额 100）；到 60 后**差额 40**；到 40 后**全额、可验证结案**；重放不重复计数 |
| 5 | 全额到账先送达，申请后送达 | 信息齐全后显示**已全额到账**，即使时间过 72h 也**不发逾期** |
| 6 | 首次提醒后用户持续不回复，推进 +24h/+48h/更久 | 首次 nudge=0；**不早于 24h 发第1次、48h 发第2次**；之后**不再发**（共 3 条） |
| 7 | 用户点"明天再提醒" | 下次提醒时间 **≥ now+24h**，且与既有最早提醒取较晚；**次数不清零**；到期前不发 |
| 8 | 用户标记"确有问题"，但无解决结果 | 状态=**待解决**，不标成功/不结案；推进 24h **不追加催办** |
| 9 | 关闭问题后，退款到账数据补达 | 到账事实**已记录可查**，但问题仍**关闭**，不重开、不催 |
| 10 | 已发首次提醒后模拟中断/重启，再恢复 | **提醒次数、处理状态完整保留**；重放不重复发提醒 |

2. **场景演示脚本（给人看）**：`python demo.py`（或按场景逐个跑），打印每个场景的「喂了什么 → 时间推进 → 系统建了什么问题/发了什么提醒 → 最终状态与结案依据」，每个场景结尾标 `PASS`。

README 里写清楚两条命令，面试官既能自己跑测试，也能看演示流水。

## 四、保证"一次过"的工程要点

- **断言要落到具体值**：问题数、状态枚举、金额/差额、提醒次数与精确时间点、结案依据——题面明确说"只断言返回 200/不为空不算数"；

- **接口要稳**：面试官可能不按你的剧本，自己拿接口喂数据，所以重复检测、乱序、状态门禁在任意调用顺序下都要成立，不能只在测试脚本的固定顺序下通过。

## 一、SQLite 的两种存在形态

| 形态 | 连接串 | 特点 |
|---|---|---|
| **内存模式** | `sqlite:///:memory:` | 数据在内存里，**进程结束即消失**，不用任何文件 |
| **文件模式** | `sqlite:///./app.db` | 本地生成一个 `app.db` 文件，程序直接读写 |

它没有"数据库服务器"，你的程序通过库直接读写，**不需要先启动一个数据库进程**。

## 二、所以"带不带数据库"根本不是问题

3. 面试官拿到代码后：
   ```
   pip install -r requirements.txt   # 装依赖（SQLite 不用装，Python 自带）

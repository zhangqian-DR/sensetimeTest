# 第一部分：完整题面（原文整理）

## 【1/3｜发现账单问题后继续跟进 — 需求、验收与交付 V0.2】

**用户需求**：发现重复扣款或退款迟迟没到时，提醒我，并帮我继续看有没有解决。只检查疑似重复消费和退款逾期，不自动删除交易，不联系商户。数据和外部效果可模拟，无需真实支付、连接银行或第三方；人民币、北京时间。不限定协议、存储、界面或实现，不要求指定 SDK/support。验收关注可观察结果，各场景独立或合并演示但不能互相污染状态。

**具体需求**：
1. 同一用户、同商户、同额且相差不超过 10 分钟的两笔不同编号交易建立一条疑似问题，每个无序交易对只有一条。三笔两两满足可产生三条并明确关联，不能称已证实错误扣款。
2. 退款自申请确认满 72 小时仍未全额到账即提醒。按退款编号关联；先到的到账数据也保留，信息齐全再判断。
3. 用户可标为：两次正常购买、确有问题、明天再提醒、已自行解决或关闭。确有问题不等于解决；疑似重复需用户明确确认解决才结案，标"用户确认"，不称已验证退款。正常/解决/关闭分开记录。
4. 首次提醒不计追加次数。未回复时距上次至少 24 小时追加，最多两次；部分到账等新数据不重置次数。用户确认有问题后等相关事实或下一项明确约定，不沿用无回复催办。
5. 明天再提醒默认延后 24 小时，与既有最早提醒时间取较晚值；明确日期需澄清时间。延期不重置次数。
6. 全额到账可验证解决，部分到账显示差额。关闭后新事实只补记录，不自动打开；新的独立交易对可形成新问题。

## 【2/3｜持续工作、用户控制与验收】

- 收到新数据或到达约定时间后应自行检查，不等待用户再次发消息；用户离开再回来能了解进展。中断恢复不遗失已确认结果，不重复处理同一事实。
- **暂停**后停止主动提醒及新操作，允许查看已有记录；恢复按最新数据和设置检查，不补发暂停期间每条过期提醒。
- **关闭**后停止自动推进，重新开启需用户明确要求。暂停/恢复不清空提醒次数或处理记录。
- 已发送消息、已发生操作如实保留。发送前已接受关闭则不能继续发；发送后关闭不声称撤回。已提交但结果未知的操作需说明未知并核实，不盲重试，不把关闭当作撤销。
- 不同用户的设置、账目、结果独立；外部说明文字不能替代用户授权或要求访问他人数据。缺失及失败不得伪装成零、成功或完成。

**验收场景（各场景独立）**：
1. 同用户同商户 09:00/09:05 各 30 元、编号不同 → 一条疑似问题，不删除交易。
2. 用户说买了两次并重放 → 记录正常，不重新打开。
3. 09:00/09:05/09:09 各 30 元 → 三个不同交易对，重放不新增。
4. 应退 100，72h 未到，再到 60 和 40 → 先剩 40，最终解决，重放不累计。
5. 全额到账先于申请送达 → 信息齐全后显示到账，不发过期逾期消息。
6. 首次提醒后持续不回复 → 不早于 24/48 小时各追加一次，此后不催。
7. 明天再提醒 → 至少延后 24 小时，次数不清零。
8. 用户确认重复扣款但无解决结果 → 保持待解决，不标成功。
9. 关闭后补到退款 → 补事实，不打开或继续催。
10. 提醒后中断恢复 → 保留计数和处理状态。

**完成标准**：每条问题有原因、相关交易、处理历史和明确结案依据；发过提醒不能算解决。

# 第二部分：初步分析（供参考，可质疑/修正）

## 1. 系统定位

这是一个**时间驱动的主动式后端服务**，不是必须接大模型的 LLM Agent：规则完全可枚举、输入输出结构化、验收是 10 个确定场景，题面无任何"必须用大模型/NLU"的信号。其"自主性"（到点自查、中断恢复、持续跟进）由后端事件 + 定时评估实现。

## 2. 两个驱动力

- **事件驱动**：交易/退款/到账/用户动作到达即处理；
- **时间驱动**：72h、24h/48h、snooze 到期需"醒来"。
- 两者统一汇入一个纯逻辑函数 `evaluate(now)`：检测 → 对账 → 提醒调度 → 状态转移。

## 3. 候选领域模型（字段由规则反推，可调整）

| 对象 | 关键字段 | 服务于 |
|---|---|---|
| AppUser | id, name | 用户 |
| Merchant | id, name | 商户 |
| Txn 交易 | **txNo(唯一)**, userId, merchantId, amount, occurredAt | 10min 配对 |
| Refund 退款 | **refundNo(唯一)**, userId, txNo, expectedAmount, **requestedAt** | 72h 计时 |
| RefundArrival 到账 | refundNo, amount, arrivedAt, **dedupKey 唯一** | 乱序/部分/全额 |
| Issue 问题 | **dedupKey 唯一**, type, status, clusterId, snoozeUntil, **nudgeCount**, first/lastReminderAt, resolution, resolutionBasis | 状态机/提醒 |
| IssueTxn 关联 | issueId, txNo | 关联展示 |
| Reminder 提醒 | issueId, kind(FIRST/NUDGE1/NUDGE2/SNOOZE), scheduledAt, sentAt | outbox，可查不真发 |
| ActionHistory 历史 | issueId, action, actor, at, detail | 审计/结案依据 |
| UserSettings 设置 | userId, paused | 暂停/恢复 |

## 4. 关键判定规则

- **疑似重复**：同 user + 同 merchant + 同 amount + `|Δ| ≤ 10min` + 不同 txNo；每个无序对一条（dedupKey=类型+排序编号对，唯一约束兜底）；**两两判断、不做链式传递**：09:00/05/11（首尾 11min）→ 2 条；09:00/05/09（首尾 9min）→ C(3,2)=3 条，共享 clusterId；措辞只能称"疑似"。
- **退款**：以申请确认时间 requestedAt 为 72h 起点；到账可多笔、乱序、先于申请（保留不报错）；**先看是否全额、再看是否逾期**；全额=RESOLVED_FULL 可验证结案、不发逾期；满 72h 未全额→逾期；部分→显示差额（应退−已到）。

## 5. 状态机（正常/解决/关闭分开）

```
重复类： OPEN → REMINDING
           ├ 两次正常   → NORMAL（误报结案）
           ├ 确有问题   → CONFIRMED_PROBLEM（待解决，停催）→ 用户确认解决 → SELF_RESOLVED
           ├ 明天再提醒 → SNOOZED → REMINDING
           └ 关闭       → CLOSED
退款类： TRACKING → OVERDUE/PARTIAL → RESOLVED_FULL（全额到账）
通用：   CLOSED 后新事实只补记录、不重开；新独立交易对形成新 Issue。
```

## 6. 提醒/时间规则

首次 nudge=0（不计追加）；未回复且距上次 ≥24h 才追加、最多 2 次（共 3 条，时间点 0/24/48h）；新数据不重置次数；标"确有问题"后停催；"明天再提醒" next=max(已有最早提醒, now+24h)，不清零；只给日期无时间需澄清。

## 7. 控制与诚实性

暂停停主动提醒/新动作、恢复不补发、不清次数；关闭冻结、只补事实；已发消息保留、发送前已关闭不发、发送后关闭不撤回；结果未知须标"未知"并核实、不盲重试、不把关闭当撤销；多用户隔离；缺失/失败不伪装成 0/成功/完成。

## 8. 架构与外部效果模拟

- 提醒写入 **Reminder 表（outbox）**，可查、不真推送；
- 时间用**可注入 Clock**，测试用 FixedClock 虚拟推进，不写常驻 while/cron；定时任务体做成可调用服务，生产再挂 cron；
- 存储建议：嵌入式 SQLite（零外部依赖、自动建表），测试用内存模式天然隔离；可平滑替换为其他数据库。

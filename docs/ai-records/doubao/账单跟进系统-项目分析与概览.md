## 1. 一句话定位

一个**时间驱动的主动式后端服务**：盯着交易与退款，发现"疑似重复扣款"或"退款 72h 未全额到账"就建立问题、按节奏提醒，直到**用户明确处理**或**事实（全额到账）结案**。不删交易、不联系商户、不做真实支付/推送，外部效果全部模拟。

这不是必须接大模型的 LLM Agent：规则完全可枚举、输入输出结构化、验收是确定场景。其"自主性"（到点自查、中断恢复）由后端事件 + 定时评估实现。

## 2. 核心概念与数据模型

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `AppUser` | id, name | 账单归属用户 |
| `Merchant` | id, name | 商户 |
| `Txn`（交易） | id, **txNo(外部编号,唯一)**, userId, merchantId, amount, occurredAt | 检测的基本输入 |
| `Refund`（退款） | id, **refundNo(唯一)**, userId, txNo, expectedAmount, **requestedAt(申请确认时间)** | 72h 计时起点 |
| `RefundArrival`（到账） | id, refundNo, amount, arrivedAt, **dedupKey 唯一** | 可分多笔、可乱序/先于申请到达 |
| `Issue`（问题） | id, type, status, **dedupKey 唯一**, userId, reason, clusterId, snoozeUntil, firstReminderAt, lastReminderAt, **nudgeCount**, resolution, resolutionBasis, 各时间戳 | 系统核心产物 |
| `IssueTxn`（问题-交易关联） | issueId, txNo | 重复类关联展示；三笔时三条共享 cluster |
| `Reminder`（提醒/消息） | id, issueId, kind(FIRST/NUDGE1/NUDGE2/SNOOZE), scheduledAt, sentAt, content | 即 outbox，"已发送"可查，不真推送 |
| `ActionHistory`（处理历史） | id, issueId, action, actor, at, detail | 完整审计 |
| `UserSettings`（用户设置） | userId, **paused**, pausedAt | 暂停开关；关闭落在 Issue 上 |

金额一律 `BigDecimal`（两位、HALF_UP）；所有时间经可注入 `Clock`，测试用 `FixedClock` 虚拟推进。

## 3. 两类问题的判定规则

### 3.1 疑似重复扣款
- 条件：同 user + 同 merchant + 同 amount + `|t1−t2| ≤ 10min` + 不同 txNo。
- **每个无序对只建一条**：`dedupKey = DUP + sorted(txNo_a, txNo_b)`，唯一约束兜底。
- **必须两两判断，不做链式传递**：09:00/05/11（首尾 11min）→ 2 条；09:00/05/09（首尾 9min）→ C(3,2)=3 条，共享 `clusterId` 明确关联。
- 措辞只能是"**疑似**"，禁止称"已证实错误扣款"。

### 3.2 退款逾期 / 对账
- 到账可分多笔、可乱序；先于申请到达的到账**保留不报错**，信息齐全后再判。
- 判断顺序：**先看是否已全额，再看是否逾期**。
  - 已到合计 = 应退 → `RESOLVED_FULL`，可验证结案，**不发逾期**（即使申请时间看起来已过 72h）；
  - now ≥ requestedAt + 72h 且 已到 < 应退 → 逾期提醒，差额 = 应退 − 已到；
  - 部分到账 → 显示差额（如到 60 则"剩 40"）。

## 4. Issue 状态机（正常 / 解决 / 关闭必须分开）

```
 重复类：  OPEN ─首次提醒─► REMINDING
             ├ 标"两次正常"   → NORMAL          （误报结案）
             ├ 标"确有问题"   → CONFIRMED_PROBLEM（待解决，停止催办）
             │                    └ 用户确认解决 → SELF_RESOLVED（结案，标"用户确认"）
             ├ 明天再提醒     → SNOOZED ─► 回到 REMINDING
             └ 关闭           → CLOSED          （冻结）

 退款类：  TRACKING(信息未齐) ─72h未全额─► OVERDUE
             ├ 部分到账 → PARTIAL（显示差额）
             └ 全额到账 → RESOLVED_FULL（可验证结案）
             （用户同样可标 SELF_RESOLVED / CLOSED）

 通用： CLOSED 后新事实只补记录、不自动重开；新的独立交易对形成新 Issue。
```

结案依据：重复类靠**用户明确确认**（不称已验证退款）；退款类靠**全额到账**；关闭是用户主动结案，与解决/正常并列。**发过提醒 ≠ 解决。**

## 5. 提醒与时间规则（就 4 个数字）

```
 首次提醒            第1次追加            第2次追加
  nudge=0             nudge=1             nudge=2
 ──├── 24h ──┼──────── 24h ────────┤  之后不再催（共 3 条）
```

- 首次不计追加；未回复才追加，**最多 2 次**；
- 部分到账等**新数据不重置次数**、不重启 24h 周期；
- 标"确有问题"后**停止无回复催办**；
- "明天再提醒"：`next = max(已有最早提醒, now+24h)`，取较晚、**不清零**；只给日期无时间需澄清。

---

## 6. 持续工作与用户控制

- **自动驱动**：新数据到达或到点即跑评估，不等用户；
- **中断恢复**：状态全在 DB，评估幂等，重放/重启不丢已确认结果、不重复处理同一事实；
- **暂停**：停主动提醒/新动作，可查；恢复按最新数据评估，**不补发暂停期间每条过期提醒**；暂停/恢复不清次数与记录；
- **关闭**：停自动推进，重开需明确；已发消息保留；发送前已关闭则不发，发送后关闭不撤回；已提交但结果未知须标"未知"并核实，**不盲重试、不把关闭当撤销**；
- 多用户隔离；缺失/失败不得伪装成 0/成功/完成。

## 7. 系统架构与驱动方式

```
 交易/退款/到账/用户动作 ─► 事件入口(REST, 幂等写入) ─┐
                                                        ├─► EvaluationEngine.evaluate(now)
 到点(72h/24h/48h/snooze) ─► Tick 入口(内部) ──────────┘     (检测→对账→调度→状态转移)
                                                                      │
                          H2 持久化(Issue/Reminder/History) ◄─────────┘
                          Reminder 即 outbox（可查的"已发送"，不真推送）
```

- 事件入口：生产=上游 webhook/用户 App，笔试=接口/脚本喂入；
- Tick 入口：生产挂 cron（@Scheduled 或外部调度），笔试=FixedClock 推进后手动调；
- 题面不要求真实调度，**不写常驻 while/cron**，只把"定时任务体"做成可调用服务。

## 9. 验收场景 → 实现映射（10 个独立场景）

| # | 场景 | 落点 |
|---|---|---|
| 1 | 09:00/05 各 30、编号不同 → 1 条疑似，不删交易 | 重复检测 + 无序对去重 |
| 2 | 标"两次正常"并重放 → 记录正常、不重开 | NORMAL + 幂等 |
| 3 | 09:00/05/09 → 3 条、重放不增 | 两两判断 + cluster 关联 |
| 4 | 应退 100，72h 未到，再到 60/40 → 先剩 40 后解决，重放不累计 | 退款对账 + 部分/全额 |
| 5 | 全额到账先于申请 → 齐全后显示到账、不发逾期 | 乱序保留 + 先全额后逾期 |
| 6 | 首次后不回复 → 24/48h 各追加、后不催 | 提醒调度 + 次数 |
| 7 | 明天再提醒 → 延后≥24h、次数不清零 | Snooze max |
| 8 | 确认重复扣款但无解决 → 待解决、不标成功 | CONFIRMED_PROBLEM 停催 |
| 9 | 关闭后补退款 → 只补事实、不重开/不催 | CLOSED 冻结 |
| 10 | 提醒后中断恢复 → 计数与状态保留 | 幂等恢复 |

## 12. 关键风险与自查点

1. 无虚拟时钟 → 无法演示 72h/24h；
2. 重复检测写成链式传递 / 未按无序对去重 → 场景 3 数量错、重放重复；
3. 退款乱序/先到数据被丢弃，或先判逾期再看全额 → 场景 5 误发；
4. 次数被新数据重置、Snooze 未取较晚、确认问题后仍催 → 场景 6/7/8 错；
5. 重放重复发提醒/计数、暂停恢复补发、关闭后自动重开 → 场景 9/10 挂；
6. 断言只看"返回 200/非空"不计入；须断言数量、状态、金额/差额、次数与时间点、结案依据。

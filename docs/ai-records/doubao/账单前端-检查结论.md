# 账单系统 — 前端页面检查结论

> 范围：Codex 最后追加的本地单页（`app/static/`、`app/main.py` 挂载、`scripts/verify_page.py`）。
> 方式：**只检查、未改动、未重新运行**。浏览器验收结果以 `reports/page-browser.json`（11 项 PASS）为准。

---

## 一、总体结论

**前端质量高、与后端契约一致，没有发现缺陷。** 属于"加分项"，且没有为了页面破坏后端任何规则。

- 纯静态 HTML + CSS + 原生 JavaScript：**无前端框架、无构建步骤、无外网资源**（favicon 为内联 SVG）；
- 挂载方式：`main.py` 挂载 `/static`，根路径 `/` 返回页面，`/docs` 继续保留 Swagger；
- 实际用 **Microsoft Edge（Playwright，headless）真实点击验收 11 项全部 PASS**，含桌面/窄屏截图，不是"资源 200 或截图"代替行为验证。

---

## 二、逐项检查

| 检查项 | 结论 | 依据 |
|---|---|---|
| **页面不自行推导业务结论** | ✅ | `app.js` 第 1 行明确；问题/差额/状态全部来自后端接口，不在浏览器里算结论或改计数 |
| **操作按钮与后端状态机一致** | ✅ | `renderDetail`（126–129）：NORMAL 仅 DUPLICATE；CONFIRM 未确认时；SNOOZE/RESOLVE/CLOSE 仅 active；REOPEN 仅 CLOSED |
| **XSS 防护** | ✅ | 统一 `esc()` 转义（11 行）；`money()` 只处理数字；验收有恶意 `merchant_name` 测试，断言无 `<img>`、`onerror` 不执行 |
| **Token 处理** | ✅ | 仅存内存与密码框，**不写 localStorage**（HTML 29 行声明）；用户/管理员 token 分开；权限由后端判定 |
| **多用户隔离** | ✅ | 切用户重置 state；`epoch/read` 机制防止旧身份/旧批次的迟到响应覆盖（68、74 行）；有切换测试 |
| **超时 / 未知结果** | ✅ | 12s AbortController，超时提示"结果可能未知，先刷新核对，勿重复创建事件"（46 行） |
| **原样重放** | ✅ | `financial` 保存 lastEvent，replay 用同一 event_id 命中幂等；切用户后校验 token（168 行） |
| **管理员时钟** | ✅ | 全局推进用 admin token；real 模式按钮禁用（55 行）；页面提示"影响所有用户" |
| **缺失不伪装成 0** | ✅ | `money(null)`→"待补充"，`money(0)`→"¥0.00"；错误身份时统计显示"—"而非 0 |
| **响应式** | ✅ | 390px 窄屏断言无整页横向溢出；有移动端截图 |
| **静态目录不泄密** | ✅ | StaticFiles 只挂 `app/static`（仅 3 个文件），不暴露项目其他路径 |
| **CSRF** | ✅ | 凭据走 Authorization 头（非 cookie），本地模拟无 CSRF 面 |
| **依赖声明** | ✅ | 运行时不需要 playwright；浏览器验收依赖单独放 `requirements-browser.txt`，README 标明可选 |

## 三、实际浏览器验收证据（`reports/page-browser.json`）

11 项检查全部 PASS、`browser_errors=[]`，覆盖：
1. 页面加载、当前用户、空数据；
2. 真实创建交易对并展示两笔原交易；
3. 确认问题不结案、用户约定到期后真实发送；
4. 切换用户清空旧身份问题与消息；
5. 退款 72h、60/40 到账、结案依据、原样重放；
6. 关闭有确认、保留历史、提供显式重开；
7. 暂停/恢复通过真实接口生效；
8. 商户外部文字转义、不执行 HTML；
9. 错误身份明确失败、不伪装零条；
10. 390px 窄屏无横向溢出；
11. 全程无浏览器脚本异常。

> 验收脚本首轮因"安全文字测试漏了 JSON 请求头"失败，已保留 `page-browser-attempt1.*`，修正后通过——失败过程如实留痕，没有把脚本错误伪装成产品通过。

## 四、小的简化 / 观察（非缺陷，无需改）

1. **SNOOZE 页面只支持"明天"（tomorrow=true，延后 24h）**，没有提供"指定具体日期时间"的输入框，因此前端也没有"只给日期→澄清时间"的交互。
   - 后端 `remind_at` 与"日期需澄清"逻辑完整，可在 Swagger 验证；前端做最小 tomorrow 入口属于合理简化。
   - 若想让页面也覆盖"明确日期"，可后续加一个 datetime 输入框，但**不影响本题验收**。
2. **SNOOZE 到期后是否继续自动追加**：这是后端口径问题（见《账单SNOOZE口径-细化(发Codex)》），前端只如实调用，责任在后端。
3. 页面每 3 秒自动刷新、后台每秒检查：本地演示会产生少量请求，无实际影响。

---

## 五、结论

- 前端**可保留、可用于演示**，明显提升"可观察结果"的直观度，且没有引入安全、隔离或业务正确性问题；
- 没有必须修正项；
- 唯一可选项：若需要，在页面补一个 SNOOZE 自定义日期时间入口（优先级低）。

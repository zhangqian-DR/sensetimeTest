## 三、实现亮点（值得在答辩时讲）

1. **原始接收独立事务先落盘**（`_record`，46–61）：后续校验/业务失败也不丢失现场，满足"已发生操作如实保留"。
2. **事件级 + 业务编号级两层去重**：canonical 身份竞争（同 event_id 同 hash=DUPLICATE、不同=CONFLICT），业务表再按 tx_no/arrival_no 查重。
3. **SUBMITTING 先提交再调外部**（`_send`，381–391）：崩溃重启后可按 operation_id 查询，而不是重发。
4. **未知结果绝不重提 submit**：`_evaluate` 开头只对 SUBMITTING/UNKNOWN 做 query，不重复调用 submit。
5. **成功只计一次**：`counted_at` 字段 + 条件计数，重放/重复核实不会把次数加爆。
6. **先足额后逾期**：保证乱序、全额先到等场景不发过时催款。
7. **数据库约束兜底**：partial unique（canonical receipt、active task）、CHECK（金额>0、枚举、count 0..2、DUPLICATE 只能 USER_CONFIRMED、RESOLVED 必须有依据）、复合 FK 带 user_id。
8. **配置 fail-fast**：非法 mode/时区/间隔/起始时间/Token 直接启动失败，不带病运行。

## 四、发现的问题与盲区（按重要性排序）

### 【问题 1，中等】"明天再提醒"后自动催办链中断，与"延期不重置次数"存在口径张力

**现象**：`SNOOZE` 不区分问题当前状态，统一把 `followup_mode` 置为 `USER_SCHEDULED`（243 行）；该约定到期发送后，`_complete` 又把 `followup_mode` 置为 `WAITING_FACT`（413–414 行）。此后 `_evaluate` 既不走 `USER_SCHEDULED` 也不走 `AWAITING_REPLY`，落到 `else: continue`（345 行）——**自动追加不再继续**。

**为什么值得注意**：
- 题面第 5 条明确"延期不重置次数"。当前实现确实没清零，但**保留下来的次数不再被使用**（剩余的自动追加不会再发），"不重置"的实际意义被削弱。
- 题面第 4 条末"不沿用无回复催办"的前提是**用户确认有问题后**；而"明天再提醒"（第 3 条）与"确有问题"是两个独立动作。用户在问题仍 OPEN、未确认有问题时只说"明天再提醒"，语义上应是**延后当前节奏**，到点后若仍无回复，自动追加应继续。
- 当前实现把"纯延后"和"确认问题后的约定"统一处理为"发一次后等事实"。

**定性**：这是 Codex **有测试固化的明确决策**（`test_snooze_and_explicit_after_quota`、`test_explicit_reminder_after_auto_quota`），不是疏忽，且能自圆其说（"用户主动约定后等回复"）。但面试官若严格按"延期不重置次数 + 未回复继续追加"理解，可能在此追问。

**建议**（二选一，均不紧急）：
- (更严谨) 区分两种语义：OPEN 状态下的 SNOOZE 到期后回到 `AWAITING_REPLY`（继续自动追加）；CONFIRMED_PROBLEM 下的约定到期保持 `WAITING_FACT`；
- (更省事) 不改代码，但在 DESIGN 里把这条口径写清楚，并准备好答辩理由。

> 注：场景 7 的字面验收（延后≥24h、次数不清零、不堆任务）当前已通过，本问题不影响场景结果，只影响完整业务语义。

### 【问题 2，低，已诚实声明】单进程/单 worker 是硬约束

- 写操作靠进程内 `threading.Lock` 串行；多个 uvicorn worker 或多进程会重复调度（虽有唯一约束兜底，但会产生冲突日志）。
- 本题**没有强制要求数据库级并发**（与上一道"月度账本"不同），单进程 + 唯一约束对本题可接受，且 README、acceptance 已明确声明"不支持多进程并发写入"。
- 答辩时强调"单 worker 启动 + DB 约束兜底"即可，无需临时改。

### 【问题 3，低，非 bug】`clock.now_ms()` 在事务内开新 session

- 模拟时钟每次读 `virtual_now` 都开独立连接（`SimulatedClock.now_ms`）。WAL 模式下读不阻塞、读到最近提交值，功能正确；仅产生额外连接/查询开销。
- 小数据量无影响，可在事务内复用时间值，但不值得为此改动。

### 【问题 4，低，观察项】逾期 issue 部分到账后，issue 自身 reason 不更新

- 部分到账后 issue 的 `reason` 仍是旧文案，但 `get_issue` 里 `remaining_amount_fen` 是实时计算的，用户能看到最新差额；下一次提醒的 content 也会用新差额。
- 属于合理设计（issue 仍未解决），无需改。

## 五、过度设计检查

**没有明显过度设计。**

- 12 张表单看略多，但每张职责单一、无冗余（用户/设置/元信息/原始接收/交易/退款/到账/问题/关联/提醒/外部操作/历史）。
- 通知四态（成功/失败/未知后成功/未知后失败）是覆盖"未知结果"的最小集合，没有多余。
- 未引入 Redis、消息队列、前端、真实认证、规则管理等范围外内容。
- "应用层锁 + 业务查重 + partial unique + CHECK"属于**纵深防御**，对"不重复处理、不重复计数"这一核心要求是值得的，不构成过度设计。
